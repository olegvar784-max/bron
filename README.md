# Бронь без конфликтов

Веб-сервис бронирования аудиторий колледжа. Итоговая лабораторная работа.
Автор: Варнавский О. В., группа К841. Преподаватель: Кривоносова Н. В.

Главное правило сервиса: одну аудиторию нельзя забронировать на пересекающееся время. Правило
действует при одновременных запросах и при работе нескольких экземпляров приложения.

| | |
|---|---|
| Вид ресурсов | аудитории, компьютерные классы, лаборатория, переговорная |
| Пользователи | пользователь (студент, преподаватель), администратор |
| Сервер | Node.js 22, Express 5, JWT (jsonwebtoken), bcryptjs |
| База данных | PostgreSQL 16 (расширение btree_gist) |
| Клиент | HTML, CSS, JavaScript без фреймворков (одностраничное приложение в `public/`) |
| Проверка кода | ESLint 9 |
| CI/CD | GitHub Actions (`.github/workflows/ci-cd.yml`) |

## 1. Правила

**Время** (проверяются на сервере, `src/lib/time.js`; клиент дублирует их только для удобства):

- аудитории доступны ежедневно с 08:00 до 22:00 по московскому времени;
- шаг выбора — 30 минут, продолжительность — от 30 минут до 4 часов, запись целиком в одном дне;
- начало не в прошлом и не позднее чем через 30 суток (по серверному времени);
- API принимает дату ISO 8601 со смещением (`2026-11-03T10:00:00+03:00`), БД хранит `TIMESTAMPTZ`;
- интервал полуоткрытый `[начало, окончание)`: 10:00–11:00 и 11:00–12:00 не пересекаются;
- цель бронирования — от 5 до 300 символов.

**Отмена.** Владелец отменяет свою запись до её начала. Администратор отменяет любую будущую запись
с обязательной причиной. Начавшиеся и завершённые записи не отменяются. Повторная отмена возвращает
409 и ничего не меняет. Сохраняются исполнитель, время и причина отмены.

**Доступ.**

| Функция | Пользователь | Администратор |
|---|---|---|
| Вход, выход, каталог, занятые интервалы (без чужих ФИО и целей) | да | да |
| Создание записи для себя, свои записи, отмена своей будущей записи | да | да |
| Все записи и владельцы, отмена чужой записи с причиной | нет (403) | да |
| Создание, изменение и отключение ресурсов, аудит | нет (403) | да |

Владелец записи определяется только по проверенному JWT; `userId` и роль из тела запроса игнорируются.
Чужая запись для обычного пользователя возвращается как 404. Физическое удаление ресурсов и записей
не реализовано: ресурс отключается (`isActive: false`), прежние записи сохраняются.

**Согласованные изменения.** Вместо Swagger UI и Postman для отдельных запросов используется curl
(разрешено методичкой); описание API — в `docs/API.md`. Добавлен маршрут `GET /api/resources/locations`
для фильтра местоположения и самостоятельная регистрация `POST /api/auth/register` (роль всегда `user`).

## 2. Сценарии

**Основной:** вход → каталог → карточка аудитории → выбор даты и просмотр занятых интервалов →
начало, окончание, цель → отметка «Подтверждаю бронирование» → «Забронировать» → сообщение
с номером записи, аудиторией, датой и временем → запись в разделе «Мои записи».

**Альтернативные:**

| Ситуация | Поведение |
|---|---|
| Ресурс отключён | 409 `resource_disabled`, запись не создаётся; в каталоге ресурс не показывается |
| Время занял другой пользователь | 409 «Ресурс уже занят в выбранное время», форма сохраняет данные |
| Неверные даты (прошлое, шаг, длительность, вне 08:00–22:00) | 400, ошибки выводятся рядом с полями |
| JWT истёк | 401, сообщение «Срок действия входа истёк», переход на вход и возврат на ту же страницу |
| Ответ потерян | кнопка «Повторить отправку» повторяет исходный запрос с тем же ключом, сервер возвращает ту же запись |
| Кнопка нажата повторно | кнопка блокируется на время отправки; на сервере дубликат исключает ключ повтора |
| Доступ к чужой записи | 404, данные не раскрываются и не изменяются |

## 3. Схема данных

```
users 1 ──< bookings >── 1 resources
users 1 ──< idempotency_keys >── 0..1 bookings
users 1 ──< audit_events
```

| Таблица | Поля |
|---|---|
| `users` | id, full_name, login (уникальный), password_hash (bcrypt), role (`user`/`admin`) |
| `resources` | id, name (уникальное), description, location, capacity, is_active |
| `bookings` | id, resource_id, user_id, starts_at, ends_at, purpose (5–300), status (`active`/`cancelled`), created_at, cancelled_at, cancelled_by, cancel_reason |
| `idempotency_keys` | (user_id, key) — первичный ключ, request_hash (SHA-256), booking_id |
| `audit_events` | at, actor_id, action, object_type, object_id, result, request_id (traceId), details |

Хранится только основной статус: `active` или `cancelled`. «Предстоит», «идёт», «завершена»
вычисляются по времени при выборке — фоновое обновление не нужно.

Ограничения: внешние ключи; `CHECK (ends_at > starts_at)`; длина цели; допустимые статусы;
согласованность сведений об отмене (`bookings_cancel_info`); главное — `bookings_no_overlap` (раздел 4).

Индексы (`migrations/001_init.sql`):

| Индекс | Запрос приложения |
|---|---|
| `bookings_user_starts_idx (user_id, starts_at DESC)` | «Мои записи»: `WHERE user_id = $1 ORDER BY starts_at DESC` |
| `bookings_resource_active_idx (resource_id, starts_at) WHERE status='active'` | занятые интервалы ресурса на дату |
| GiST-индекс ограничения `bookings_no_overlap` | проверка пересечения при вставке |
| `bookings_starts_idx (starts_at DESC)` | список всех записей администратора с фильтром даты |
| `audit_events_at_idx (at DESC)` | просмотр аудита |

## 4. Защита от двойного бронирования

Выбран механизм «ограничение PostgreSQL»:

```sql
CONSTRAINT bookings_no_overlap EXCLUDE USING gist (
    resource_id WITH =,
    tstzrange(starts_at, ends_at, '[)') WITH &&
) WHERE (status = 'active')
```

Почему проверка «найти свободное время → вставить» недостаточна: два запроса могут одновременно
прочитать, что интервал свободен, и оба выполнить вставку. Ограничение проверяется самой БД
в момент вставки: из двух конкурирующих транзакций вторая ждёт первую и после её фиксации получает
ошибку `23P01`. Поэтому правило соблюдается при любом числе экземпляров приложения — блокировок
в памяти процесса нет.

Последовательность создания (`src/routes/bookings.js`, строки 65–111), всё в одной транзакции (`tx`, `src/db.js`):

1. Вставка ключа повтора `INSERT ... ON CONFLICT (user_id, key) DO NOTHING` (строки 69–72).
2. `SELECT ... FROM resources WHERE id = $1 FOR SHARE` и проверка активности ресурса (строки 76–78).
3. `INSERT INTO bookings` — пересечение отклоняет ограничение БД (строки 82–85).
4. Привязка ключа к записи и событие аудита (строки 87–89), фиксация.
5. Ошибка `23P01` → откат всей транзакции, событие аудита `rejected`, ответ 409
   «Ресурс уже занят в выбранное время» (строки 103–107). Частично сохранённых данных не остаётся.

**Конкурентное отключение ресурса.** Создание записи держит `FOR SHARE` на строку ресурса,
`PATCH /api/admin/resources/{id}` — `FOR UPDATE` на ту же строку (`src/routes/admin.js`, строка 90).
Порядок одинаковый: сначала строка ресурса. Если отключение зафиксировано первым, создание увидит
`is_active = false`; если первым идёт создание, отключение подождёт его завершения.

**Конкурентная отмена.** Строка записи блокируется `FOR UPDATE` (строка 136), состояние проверяется
после блокировки. Вторая отмена получает 409 `already_cancelled`, второе событие об успешной отмене
не появляется. Обновление записи и аудит сохраняются в одной транзакции.

## 5. Повторные запросы (Idempotency-Key)

- Клиент создаёт ключ `crypto.randomUUID()` перед первой отправкой формы и хранит его, пока не
  изменятся ресурс, дата, время или цель (`public/app.js`, обработчик отправки формы, строка 216).
- Сервер вычисляет отпечаток нормализованных данных (ресурс, начало и конец в UTC, цель) — SHA-256
  (строки 37–46).
- Тот же ключ и те же данные → 200 и исходная запись без новой вставки.
- Тот же ключ и другие данные → 409 `idempotency_conflict`.
- Уникальность ключа обеспечивает первичный ключ `(user_id, key)`. Одновременный повтор ждёт
  завершения исходной транзакции и затем получает её результат; нарушение уникальности не выходит как 500.
- Если исходная транзакция откатилась (например, конфликт времени), ключ не сохраняется и повтор
  выполняется как новая попытка.

## 6. Настройка и запуск

Требуется: Node.js 22, npm 10, PostgreSQL 16 с расширением `btree_gist` (входит в стандартную поставку).

```bash
npm ci                                  # зависимости
cp .env.example .env                    # задать DB_PASSWORD, JWT_SECRET, SEED_PASSWORD
createdb -U postgres bron               # база данных
npm run migrate                         # миграции (одним процессом, рекомендательная блокировка 841001)
npm run seed                            # учебные данные (повторный запуск пересоздаёт их)
npm start                               # сервер и клиент: http://localhost:8080
```

Переменные окружения (`.env.example`): `PORT`, `NODE_ENV`, `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`,
`DB_PASSWORD`, `JWT_SECRET`, `JWT_TTL` (по умолчанию 2h), `SEED_PASSWORD`, `LOG_FILE`.
В режиме `production` запуск без `JWT_SECRET` запрещён. Файл `.env` в репозиторий не попадает.

**Демонстрационные учётные записи:** `ivanov`, `petrova` (пользователи), `admin` (администратор).
Пароль задаётся переменной `SEED_PASSWORD` при `npm run seed`; если она не задана, скрипт генерирует
случайный пароль и выводит его один раз в консоль. Пароль передаётся преподавателю лично.

Адреса: приложение — `http://localhost:8080`, API — `http://localhost:8080/api`,
описание API — `docs/API.md`, проверки — `/health/live`, `/health/ready`.

Учебные данные: 6 аудиторий (одна отключена), записи всех состояний — завершённая, будущие активные,
отменённая и идущая сейчас. Данные вымышленные, реальные персональные данные не используются.

## 7. CI/CD

Конвейер `.github/workflows/ci-cd.yml`:

1. **build:** получение кода → `npm ci` → `npm run lint` → `npm run build` (сборка в `dist/` с проверкой
   загрузки всех модулей) → артефакт `bron-<sha>`.
2. **deploy** (`needs: build`, только push в `main`): среда `staging`, PostgreSQL 16 как сервис →
   загрузка артефакта → `npm ci --omit=dev` → `npm run migrate` → `npm run seed` → запуск → проверка
   `/health/live` и `/health/ready`.

Секреты `DB_PASSWORD`, `JWT_SECRET`, `SEED_PASSWORD` хранятся в Settings → Environments → staging
и в журнал не выводятся. `concurrency` не допускает двух публикаций (и двух миграций) одновременно.
Если сборка или проверка кода падает, задание deploy не запускается. Автотесты API в конвейер не входят.
